# Brazy Roadmap

Brazy is a fork of [Hazy](https://github.com/Superstar64/Hazy), Freddy Cubas's
(Superstar64) Haskell compiler. It is a testing fork: a place to try ideas and
experiments without putting review work on Freddy. Freddy reviewed the first
draft of this roadmap on 2026-10-09 and his answers are folded in below.

The roadmap draws on two sources:

- Hazy's README: what is missing, what is a known bug, and its two milestones
  (standard library, bootstrapping).
- The [Aith](https://github.com/superstar64/aith) README, which says Aith is
  dead and that "I plan to eventually integrate all of it's ideas into Hazy".
  Freddy still plans to do that himself in Hazy, slowly. The versions here
  are experiments.
- Freddy's notes on strictness, passed on by Chris on 2026-10-09: a three-page
  specification, "A Bipartite Strict-vs-Lazy Lambda Calculus", and a short
  message on calling strategies. They are summarised under Track B.

Steps marked *(proposed)* are this fork's guess at how to do something.
Neither README specifies them and Chris has not yet confirmed them.

## Ground rules

These apply to all work in this fork.

1. **All work is open source.** Development happens in the public repository;
   nothing is kept in a private branch or a closed component.
2. **Same licenses as Hazy.** The split in Hazy's README is kept as is:
   - compiler and other components: GPL-3.0-only (`LICENSE`);
   - standard library and runtime (`library/`, `runtime/`): Boost Software
     License 1.0 (`LICENSE-BSL`);
   - code generated by the compiler follows the license of its input.

   New files take the license of the directory they are in, so the Rust
   runtime under `runtime/` is Boost-licensed. Copyright notices are not
   removed. No dependency (Rust crates included) or imported code may be added
   that is incompatible with these licenses.
3. **The git history is kept.** The fork carries all of Hazy's commits (489 at
   the time of forking, up to `7e94713`) with their original authorship.
   - Upstream commits are never rewritten, squashed, or dropped.
   - `master` is never force-pushed.
   - Code brought in from elsewhere (for example from Aith) is brought in with
     its history or, where that is not practical, with the source repository
     and commit named in the commit message.
   - Work is kept as ordinary commits on top of upstream so that any of it
     could later be offered back to Hazy.
4. **No pull requests to Hazy until Chris says so.** Nothing is sent upstream
   on the strength of being written. An idea has to be tested here first, and
   Chris decides when something is ready to offer. When that happens, Freddy
   has asked that pull requests be small and reviewable.

## Decisions

All by Chris on 2026-10-09 unless noted.

- **The LLVM backend is the first priority.** Track A issues (Hazy's bugs and
  missing features) are fixed as the backend work runs into them, not as a
  separate phase beforehand.
- **The native backend emits LLVM IR.** Freddy called LLVM the ideal and gave
  one caution: LLVM IR differs per platform. He was unsure whether C should
  sit in between; this fork does not go through C.
- **The runtime for the LLVM backend is written in Rust.**
- **The lowering is Core, then sequent calculus, then AxCut with the linear
  discipline, then LLVM IR.** This is the strategy of Chris's other compilers
  (Meadow's Silo backend, Powder's second backend). The reason is that Freddy
  wants to experiment with linearity, Perceus-style reference counting and
  functional-but-in-place reuse, and the linear form of AxCut gives all three
  a place to live.
- **Javascript is run with Bun, not Node.** Decided by Chris later the same
  day.
- **The Javascript backend is the oracle.** Native output is checked against
  what the Javascript backend produces, except where the Javascript backend
  is itself wrong.

## Where Hazy stands today

- About 34,000 lines of Haskell, built with GHC 9.14 and Cabal 3.16.
- Pipeline: parse, resolve, check, lower to Core, generate Javascript
  (`Generate.Go.*` turns `Core.Tree.*` into `Javascript.Tree.*`).
- A minimal package system (`--pack`, `--package`), with `hazy-internal` and
  a test-only `base` loaded by default. A package's `artifacts` are
  Javascript.
- A `Levity` kind with `Lazy` and `Strict`, levity-polymorphic constructor
  fields, and two universe levels (`Small` and `Large`).
- Tests: parse, resolve and check failures, files that must compile, and
  programs that are run and compared against expected output (27 at the time
  of forking, under Node only; they are run with Bun now).

## The native pipeline

```
Core ──▶ Sequent ──▶ AxCut ──▶ linear AxCut ──▶ LLVM IR ──▶ native
                       │                                      │
                 reference machine                      Rust runtime
```

All of the passes are written in Haskell inside the compiler, so that the
compiler can still compile itself one day. Rust is the runtime only.

1. **Sequent.** Core is translated to a focused, call-by-value sequent
   calculus (λμμ̃): producers, consumers, and statements that cut one against
   the other. Laziness is explicit. A lazy value is a thunk object that is
   forced by a consumer and then overwritten with its result, so everything to
   do with laziness is visible in the IR and can be optimised by ordinary
   passes. Every binder records how it is evaluated (by need, by value or by
   name), following Freddy's strictness design under Track B. Haskell 2010
   code is by need everywhere except strict fields, so the front end produces
   little else at first, but the IR is ready for strict schemes when they
   arrive: a by-value binder holds an evaluated value and makes no thunk.
2. **AxCut.** Cuts are normalised until a variable stands on one side, giving
   AxCut's small set of statements (`let`, `new`, `switch`, `invoke`,
   `substitute`, jumps and primitives) over a positional environment. The
   lowering threads the exact list of live names, so nothing downstream needs
   a liveness analysis.
3. **Linearisation.** The program is rewritten so that every name is used
   exactly once: an explicit *share* where a name is used again and an
   explicit *erase* as early as a name is no longer needed. Reference counting
   is then exact and not a heuristic, which is Perceus's result reached from
   the sequent side. Two things build on it:
   - **Reuse (FBIP).** A `switch` that held the last reference to a block
     hands its arm a reuse token, and the next allocation of the same size on
     that path builds in place.
   - **Borrowing.** A parameter a function only reads is borrowed, so the
     callee counts nothing.
4. **LLVM IR.** Each block of linear AxCut becomes an LLVM function and every
   jump and invoke a tail call. What differs per platform (target triple, data
   layout, calling convention) is kept in one per-target layer.
5. **Rust runtime.** A static library the generated code links against: the
   heap (size classes, counts, lazy bounded freeing), thunk evaluation and
   update, and the primitives that
   `runtime/javascript/Hazy.mjs` provides today.

Lessons already paid for in Meadow and Powder that apply here:

- Keep an AxCut reference machine beside the IR. It pins down what the IR
  means and tests the lowering before code generation is involved.
- On aarch64, tail calls with stack-passed arguments hit an LLVM `tailcc` bug;
  Silo passes arguments in registers only and spills the rest to a per-thread
  area.
- Compile pattern matches to decision trees that never backtrack, and decide
  per arm whether a `switch` consumes its scrutinee. Otherwise scrutinees stay
  alive and reuse cannot happen.
- Cap the number of owning copies made per block during borrow inference, or
  linearisation can take exponential time.
- The Javascript backend and the native backend can differ wildly in running
  time when sharing is lost. Suspect lost sharing in library or generated code
  before suspecting the runtime.

the AxCut machine as it does as Javascript.

- [x] Binders in `Sequent` carry a calling strategy. By need and by value are
      recorded and printed; nothing reads them yet, and nothing makes a

- [x] `AxCut` IR (`compiler/AxCut/Tree.hs`), focusing and the lowering from

- [x] An AxCut abstract machine in Haskell (`AxCut/Machine.hs`).
      `--run-axcut` runs a program on it
- [x] The `Hazy` module over a small set of primitives

- [x] `tools/test.sh` runs every `test/run` program on the machine as well

What M1 leaves as it is, on purpose:

- The whole program is translated at once, from the Core of every module

  package on its own is part of M2.
- Pattern matching keeps Core's shape: a branch that fails jumps to the next,
  and where the next is not small it is a consumer that is allocated. Turning
  this into decision trees is part of M5.
- `substitute` copies and drops freely. Making every name used once is M4.

### M2. Native hello

Done on the `m2-native` branch. `test/run/hello` runs natively, and so do 21
of the other 29 programs; the rest need a primitive that is M3's.

- [x] LLVM IR generation from AxCut (`compiler/LLVM/FromAxCut.hs`) for arm64,
      behind `--native PATH`. `--debug-llvm` prints the IR
- [x] Rust runtime crate in `runtime/native`: allocation and the primitives.
      Forcing a thunk and giving a value to a consumer are emitted as LLVM IR
      with every program, because they end in tail calls into the program
- [x] `tools/build.sh` builds the runtime, and the compiler has `clang`
      compile the IR and link the executable
- [x] An LLVM page in `:ir`
- [x] Check: `test/run/hello` runs natively, in `tools/test.sh`

How it works, and what it leaves:

- A value is one 64-bit word. An odd word is an `Int` or a `Char`. An even
  word is the address of a block, whose first word says what it is.
- Every method of an object is a function, entered with a guaranteed tail
  call (`tailcc` and `musttail`), so a program runs in constant stack. AxCut's
  environment exists only in the compiler: inside a function each value is
  an LLVM value and `substitute` costs nothing.
- A call passes eight arguments in registers and the rest through a fixed
  area of memory, after Silo, to stay clear of stack arguments in tail calls.
  That number is the one thing in a `Target` so far.
- Nothing was freed. That came with M4.
- The whole program was compiled at once. Compiling a package on its own
  came after M3.

### Separate compilation

Done on the `separate-compilation` branch. A program is no longer compiled
together with its packages: `hello` goes from 3,142 lines of LLVM IR to 330.

- [x] A package compiled on its own. `--native-object PATH` compiles the
      modules that are not a package's to an object, and a package keeps its
      object as `native.o` beside its `package` file
- [x] A program links against the objects of the packages it loads.
      `--native` compiles only the program's own modules; `--whole` asks for
      the old way, with everything compiled together
- [x] `tools/build.sh` builds the objects of `hazy-internal` and `base`
- [x] Check: a test package (`test/package/shapes`) built and used from a
      program, as Javascript and natively, in `tools/test.sh`

How it works, and what it leaves:

- A unit is the modules that are not a package's. Its definitions are seen
  from outside under their own names, and what it uses of other units is
  declared and left to the linker.
- The `Hazy` module's primitives, which are written in the sequent calculus,
  are compiled with the package that has the module.
- The instances for tuples are made where they are used, since there is one
  for every size. Each unit that uses one compiles it, and the linker keeps
  one (`linkonce_odr`).
- Forcing is defined once, in the unit that is the program, and packages
  declare it.
- The linker drops what is not reached (`-dead_strip`).
- Making a package is still two commands, `--pack` for the headers and the
  Javascript and `--native-object` for the object. They could be one.
- Nothing is optimised across units. The whole-program way is kept for when
  that matters, and for the analyses of M5 that want to see everything.

### M4. The linear discipline

Done on the `m4-reference-counting` branch. Native programs free what they
no longer use, cycles included, and every `test/run` program passes with all
of its counts checked at every collection.

- [x] Share and erase, every reference owned. AxCut's `substitute` is where a
      value is shared or erased: one that is wanted more times than it is held
      is shared, and one that is held and no longer wanted is erased. Every
      other statement consumes what it takes
- [x] Exact reference counting in the runtime (`runtime/native/src/heap.rs`),
      with lazy bounded freeing: a block whose count reaches zero waits on a
      list, and a few are taken apart at each allocation
- [x] Cycle collection, by tracing (see below)
- [x] Check: the test suite passes with every count verified.
      `HAZY_GC_VERIFY` works every count out again at each collection and at
      exit, and `tools/test.sh` runs the native tests with it and with
      collections forced often. A new test, `cycles`, makes values that refer
      to themselves and checks that tracing frees them

How it works:

- **Who owns what.** A function owns its arguments and what it captured. A
  closure can be entered many times, so entering it shares what it captured,
  unless that was the last reference to it, when the closure is freed and
  its contents are simply taken. The same is done when a constructed value
  is taken apart by `switch`. A thunk is entered once and its contents are
  taken. A primitive borrows its arguments.
- **What is not counted.** Numbers that fit in a word, and definitions at the
  top of a program.
- **Cycles.** Chris chose a tracing collector as the backup, on 2026-10-09,
  over trial deletion and over leaking them. Counting does the everyday work
  and tracing frees what counting cannot.
- **Roots without a stack.** Because every call is a tail call, nothing is
  alive across a call. At the start of a function the only live values are
  the ones it was given, and the values of top-level definitions that have
  been forced. So each function starts by checking whether a collection is
  due, and if it is, hands over what it holds. No stack maps are needed.
- **Verifying.** With everything reachable known, every count can be worked
  out from nothing and compared. A lost reference or one given up twice is
  reported at the first collection after it happens.

The collector did not stay: see the end of this section. Freddy never
planned one: his plan is
to have no cycles to collect, by lambda lifting the bindings that refer to
themselves, with a low-level linear system that rules cycles out before the
program runs. Chris decided on 2026-10-10 to keep the collector for now and
to take it out when that is in place. Taking local functions out to the top (see M5), with the variables they
use passed to them, already removes the cycles those made. What remains is
functions that use variables of where they are, which need those passed to
them, and values defined by themselves, such as `ones = 1 : ones`.

Freddy on values defined by themselves, 2026-10-10:

- At the top of a module a cycle is fine, because what is at the top is
  never freed.
- Anywhere else, recursion is to be rewritten so that it does not share:
  as `fix f = f (fix f)`, and not as `fix f = let go = f go in go`. Each
  time the value refers to itself it is made again, so nothing points back
  at itself and there is no cycle. The cost is in his words "worse big O in
  some cases": a local `ones` takes memory for as much of it as is used,
  where the shared one takes a single cell.

What that means here, to be weighed when it is built:

- It costs time as well as memory. A local value that is defined by itself
  so as to remember what it has worked out, such as
  `fibs = 0 : 1 : zipWith (+) fibs (tail fibs)` in a `where`, works every
  earlier part out again each time it looks back, and goes from a number of
  steps in line with its length to one that doubles with it. The same
  definition at the top of a module keeps its sharing.
- A local value that is defined by itself and uses nothing of where it is
  can be taken out to the top, as closed functions already are, and keep
  its sharing. It is then never freed, which is the same bargain as any
  other definition at the top. `Sequent.Hoist` leaves thunks where they are
  today for that reason, and this would change that for the ones that refer
  to themselves.
- Only values that are defined by themselves and do use variables of where
  they are need the rewrite, and those are the ones that pay.

Asked about the cost in time, Freddy confirmed the plan the same day and
said he is not sure how bad it would be in practice. His reason for counting
references in the first place is that Hazy should follow C++'s "you pay for
what you use", with no garbage collection. He would like a warning where the
rewrite loses sharing. So:

- [x] Rewrite the recursion of local values so that it does not share, as
      above (`compiler/Sequent/Hoist.hs`). A thunk in a `let` or a `where`
      that refers to itself, by itself or by way of the others it is defined
      with, is no longer an object that holds itself. If it uses nothing of
      where it is, it goes to the top of the program, where it is worked out
      once and kept: `fibs` in a `where` is still as quick as it was. If it
      does use a variable of where it is, it becomes a function of those
      variables that works the value out, and each place it refers to itself
      is a new thunk that calls the function again. Everything else that
      uses it still sees one thunk, worked out once
- [x] Warn where that is done to a value. The compiler says, in yellow and
      even when it is asked to be quiet, which value in which definition is
      worked out again each time it refers to itself, and that at the top of
      the module it would be worked out once. It has no place in the source
      to point at: the sequent calculus does not carry one
- [x] Take the cycle collector out. The runtime counts references and does
      nothing else. `HAZY_GC_THRESHOLD` and `HAZY_GC_STRESS` are gone, and a
      compiled function no longer starts by asking whether a collection is
      due
- [x] Keep the checking, and make it say that there are no cycles. A
      program compiled with `--checked` hands over what it holds at the
      start of each function when `HAZY_CHECK` is set, every count is worked
      out again, and now a block that nothing reaches is an error as well.
      `tools/test.sh` compiles every native test that way, so each of them
      shows that it makes no value that holds itself and loses no reference

What this leaves:

- Functions written in the sequent calculus by hand (`Sequent.Runtime`) are
  dealt with the same way, since they go through the same pass. The
  instances for tuples refer to themselves to reach their default methods,
  and are made again where they do.
- A value that goes to the top is never freed. That is the bargain of any
  definition at the top, but it is now made for the program without being
  asked.
- The warning names the definition and the value, not the line.
- The packages are not compiled to be checked, only the test programs and
  one test that is compiled whole. What a package's function gets wrong
  is still found, at the start of the next function that is checked.

What it left, all three dealt with in M5:

- Counting was done by calls into the runtime, and for every value.
- A collection was due after a fixed amount of allocation, whatever had been
  freed since.
- A block was two words bigger than its contents: a header and a count.

### M5. Reuse and borrowing

Done, over the branches whose names start with `m5`. Counting is done in the
program's own code, values are built in the place of ones just taken apart,
what is certain to be evaluated is evaluated at once, a function is lent
what it only reads, and matching looks at each value once. There are four
benchmarks that say what each of these is worth.

What is left of the cost of laziness is what the language asks for: a lazy
list is a thunk for each element and one for the rest. Taking that away
means being told that something is strict, which is the first experiment
under Track B.

The first part:

- [x] Counting in the program's own code. Sharing and erasing are a few
      instructions where they happen, and the runtime is called only when a
      count reaches zero. Values known to be numbers are not counted at all
- [x] A header of one word. The count of references is the upper half of the
      header, so a block is one word bigger than its contents and not two
- [x] No allocation for a constructor with no fields. There is one block for
      each tag, which is not counted
- [x] Collections only when the heap grows. A collection is due when the heap
      is twice what was alive after the last one. Memory that counting frees
      does not bring one nearer, so a program with no cycles is hardly ever
      traced
- [x] A thunk with one owner gives its value over unshared and is freed, so
      a value that came out of a thunk can still be the only reference
- [x] Reuse (FBIP). When `switch` takes apart the last reference to a value,
      and a value with as many fields is built before control goes anywhere
      else, it is built in the same block
- [x] `--no-reuse` switches reuse off, so its effect can be measured
- [x] Clauses that test the same variable are one test. The value is looked
      at once, and no clause holds it while another is tried. This is the
      part of "decision trees" that reuse needed
- [x] Arguments are built before the function is looked up, so that a call
      such as `go (x : acc) xs` builds its cell while it still can in place
- [x] A benchmark set (`bench/`, `tools/bench.sh`) that reports what each
      program allocated with and without reuse

- [x] A method of a known instance is used directly. Every instance at the
      top of a module that needs nothing has its methods as definitions of
      their own, and `x + 1` at `Int` goes straight to the one for `+`
      without looking at the instance
- [x] Numbers written at `Int` and at `Integer` are numbers in the compiled
      program, and are not made from an `Integer` as it runs
- [x] Forcing something that is already a value allocates nothing. The code
      that takes the value is entered with it, and the consumer that would
      have waited for it is never made

- [x] A known function is called with all of its arguments at once
      (`compiler/Sequent/Uncurry.hs`). A definition that is functions inside
      functions has a second entry, called by its name and then `direct`,
      that takes every argument together, and a call that has them all goes
      there and makes nothing. The evidence a definition takes counts as its
      first arguments. A definition known to be a function is not forced
- [x] A consumer that is named and used once is put where it is used, and a
      thunk that is forced once, outside any function, is evaluated where it
      is forced (`compiler/Sequent/Simplify.hs`). The condition of an `if`
      was delayed and then looked at straight away

Blocks allocated, as M5 has gone on:

| Program | Reuse alone | Instances, numbers, forcing | Direct calls, simplifying |
| - | - | - | - |
| `reverse`: reverse 100,000 numbers ten times | 14,001,149 | 8,100,632 | 2,900,343 |
| `map`: three maps over 100,000 numbers | 19,302,200 | 11,901,656 | 6,301,129 |
| `tree`: 20,000 insertions into a search tree | 35,909,660 | 22,708,303 | 10,747,020 |

- [x] Every comparison of `Int` and of `Integer` is written out in
      `Hazy.Helper`. Only `<=` was, and the rest went through the defaults of
      `Ord`, with its evidence, for every comparison

With that the three allocate 1,200,270, 4,601,056 and 3,170,117 blocks and
run in about 0.03, 0.07 and 0.06 seconds. Where M5 began they took about
0.12, 0.17 and 0.4. `reverse` rebuilds every cell in place, and is down to
twelve blocks for each number it reverses.

- [x] Small functions are put where they are called
      (`compiler/Sequent/Inline.hs`): a call that gives every argument, of a
      function that is small and does not call itself. It is done three
      times over, each from the definitions as they were the time before,
      so it reaches three calls deep and always ends. `x < y` at `Int` was a
      call of a method that made a thunk, called a primitive and called
      `not`; it is now the primitive and a choice
- [x] The simplifier goes on from there (`compiler/Sequent/Simplify.hs`). A
      value that is constructed and at once taken apart is not constructed.
      A consumer that is only given constructed values, each choosing its
      own alternative, is put where they are. A value that is forced is
      itself. A name for a number, a constructor with no fields or a
      definition is written as what it names, and a definition that is only
      such a value, as `otherwise` is, is written as it
- [x] The block that is kept back also goes with a consumer of something
      that is forced

- [x] More of the same in the simplifier. A function that is written where
      it is called is its body. One thing in a `let` that does not refer to
      itself is only named. A name for a name is written as that name. A
      thunk that is forced as soon as it is named is evaluated first. With
      these ``acc' `seq` total acc' xs`` is an addition and a call, and
      makes nothing

With those the three allocate 800,243, 3,101,041 and 974,695 blocks and run
in about 0.02, 0.05 and 0.03 seconds. `tree` builds 289,045 nodes in place.

- [x] What is certain to be evaluated is evaluated at once
      (`compiler/Sequent/Strict.hs`). For each function it is worked out
      which parameters are forced on every path, before the function gives
      anything back and before anything is printed. Where such a function is
      called with every argument, those arguments are evaluated first and
      passed as values, and a thunk that is given a name and is certain to be
      forced after is evaluated where it is. Neither makes an object. A call
      of a function by itself is taken to force what the whole is found to,
      so `go (n - 1) (acc + n)` keeps no chain of additions waiting, with no
      `seq` written. A name that has been forced is written from there on as
      the name of its value, so what is kept in a constructor is the value
      and not the thunk it was
- [x] A test of what must be left alone (`test/run/demand`): an argument
      that is used on one path, two that change places at each call, a seed
      that the last call does not look at, the rest of a list, and what an
      action is given before the actions in front of it have run

With that the three allocate 400,180, 2,601,033 and 299,333 blocks. In
`tree`, `build` makes nothing each time round: the next seed and the tree
with one more in it were both thunks. `count` no longer delays `from + 1`.

What it does not do:

- A function that is passed around is called as it was, with thunks, and
  still forces what it is given: nothing is known of who calls it, so it
  gains nothing. Only the entry of a definition that takes every argument
  together is different. Nothing gets to that but a call that names the
  definition, and each of those evaluates first what the entry is certain
  to force, so the entry takes those as values and does not force them.
- It goes two calls deep. What a function forces is first worked out with
  nothing known of the functions it calls, and then once more with what
  was found for them. Functions that call each other get less than one
  that calls itself.
- A program that was going to fail may fail differently: if two things
  would each stop it, the one that is evaluated first now may not be the
  one that was. A program that does not fail prints what it did.
- `trace` is not counted as something that is seen, so what it prints may
  come in another order.

The rest:

- [x] Reuse across calls. In `tree` a node is rebuilt only after a comparison
      and a recursive call, which are elsewhere in the code. The block that
      is kept back now goes on past where control divides, and when the
      value is built by a consumer that is made here and entered later, the
      block goes with the consumer, as one more thing it holds. While it
      waits it is a husk: a block that holds nothing, and is given up like
      any other if nothing comes to be built in it. `tree` builds every node
      on the way back up in the block of the one it took apart on the way
      down: 271,507 of them, and 2,898,613 blocks in all where it was
      3,170,116
- [x] Borrowing. A function that only reads a parameter can take it lent:
      it counts nothing for it, or for what it reads out of it, and whoever
      lent it goes on holding it. Which parameters those are is worked out
      on the sequent calculus (`compiler/Sequent/Borrow.hs`): the ones that
      hold a value and are only taken apart, given to a primitive, or passed
      on to a function that only reads them too. Such a definition has a
      second entry, called by its name and then `lent`, that takes them so
      (`compiler/LLVM/FromAxCut.hs`). Inside it a lent value is copied and
      dropped for nothing, and a use that has to own it, such as keeping it
      in a constructor or giving it back, shares it there and then.

      A call goes to the second entry only when something keeps each such
      argument alive until the function is done. Nothing is left of a caller
      but the consumer it passes, so that has to be what does: it holds the
      value, or holds the thunk the value was forced out of, or, for what
      the caller was lent itself, holds what keeps that alive. So lending
      never makes a value live longer than it did; a caller that has no
      more use for a value hands it over as before, to be freed or built on.

      A new benchmark, `member`, searches a tree of 20,000 numbers 200,000
      times while keeping it. All 3,003,785 steps down the tree are lent,
      and it runs in about 0.026 seconds where it took 0.041 (on x86-64).
      `--no-lend` switches lending off. A test, `test/run/lend`, has the
      uses that have to own what was lent

      What it does not do: a value that is lent and then held by an object
      that is made, such as the consumer of a call that is not the last
      thing a function does, is shared for it. A function that is lent to has
      two copies of its code where it had one. And the LLVM page of `:ir`
      shows a definition without its second entry
- [x] Functions that are defined inside a definition and use nothing of
      where they are become definitions of their own, at the top of the
      program (`compiler/Sequent/Hoist.hs`). A `go` in a `where` is then made
      once and not each time control passes it, and what calls it knows which
      function it is
- [x] Everything in the output is called by its whole path. A function taken
      out of `total` in `Main` is `Main.total.go`, and the code of an object
      is the definition it is in and then every object around it, as
      `Main.count.go.k%5`. Nothing is called `closure.52` any more, and no
      two things can be called the same
- [x] Forcing a thunk that has been evaluated already makes nothing. Where
      something is forced, the code that takes the value was entered at once
      only when it was a value as it stood. A thunk that had been evaluated
      went the long way: a consumer was made, and the runtime read the value
      out and gave it to that. Now the value is read out where the forcing
      is, and the consumer is not made. `map` allocates 2,400,950 blocks
      where it allocated 2,601,033, and `member` 1,294,330 where it
      allocated 1,494,354
- [x] What is left of the cost of laziness is not for this milestone. `map`
      makes eight blocks for each number it maps: the cell, a thunk for
      `f x`, a thunk for the rest of the list, and what forcing those needs.
      The thunks are what a lazy list is, and only being told, with a strict
      function or a strict field, would remove them: see "Strictness in type
      schemes" under Track B
- [x] Lambda lifting. A local function that does use variables of where it
      is goes to the top as well, with those variables as arguments before
      its own, and every use of it passes them. Functions defined together
      are given the same variables, since they may call each other. Used as
      a value, it is the function once given its variables. No function
      defined in a `let` or a `where` is an object that holds itself any
      more, which is the first step of Freddy's plan to have no cycles, and
      calls to them are direct. Left where they are: local values (thunks),
      and a function that uses a consumer of where it is, which cannot be
      passed as an argument
- [x] The rest of decision trees: tests on different variables, and on what
      is inside a constructor. Clauses were put into one test only while
      each tested the same variable against a constructor of its own. A
      second clause for the same constructor started again from the top,
      and looked at the value again. Now the clauses that test a variable
      against the same constructor share an alternative, even when they are
      not next to each other, and what each goes on to do is tried in turn
      inside it in the same way (`match` in `compiler/Sequent/FromCore.hs`).
      The fields have the same names for all of them, so a next test of a
      field, or of another argument, is one test as well. In
      `inside (Just (x : y : _))` after `inside (Just [x])` each of the
      three values is looked at once. A test, `test/run/patterns`, has
      these, with arguments that must not be looked at

      What it does not do: it takes the tests in the order the clauses have
      them, and does not choose which variable is best tested first. A
      clause that names something with `let` before its next test is tried
      by itself from there

### M6. Bootstrapping

Goal: Hazy, compiled by Hazy through the native backend, compiles its own
source and passes `tools/test.sh`.

Where it stands (2026-10-12). Hazy resolves its own compiler's source:
`hazy -XStableImports --resolve compiler` passes, and is run on every
change. Checking it, with `--check` in place of `--resolve`, stops at once:

```
[error UnsupportedFeature]: unsupported feature: GADTs
```

The checker stops at the first thing it cannot do, so what lies behind that
is not known from running it. Counting in the source says this much, of 466
modules and about 42,700 lines:

| | |
| - | - |
| Declarations in GADT syntax | 50, in 43 modules |
| ... that are ordinary types written that way | 3 |
| ... that hide a type or carry a context | 6 |
| ... whose constructors say more of the type than its parameters do | 41 |
| Types with `forall` in them | 46, in 28 modules |
| Standalone kind signatures (`type T :: ...`) | 108 |
| `deriving` of `Show`, `Eq`, `Ord`, `Enum`, `Bounded` | about 330 clauses, which work as of the `deriving` clause fix |
| `deriving` of `Read` | 3 |
| `deriving` of `Traversable` | 1 |

So GADTs come first and are most of the work. The 41 are not incidental:
the trees are indexed by the stage of the compiler they belong to and by
the names in scope, and matching on a constructor is what tells the checker
which stage or scope it is in. They cannot be written another way without
writing the compiler another way. What has to be built is constructors
with result types of their own, and matching that brings the equalities a
constructor stands for into scope for its branch.

The order to take it in:

- [x] Declarations in GADT syntax, and constructors with a result type of
      their own. The resolver already carried them; the checker threw them
      out. A constructor now says what type it makes (`Shape`, in
      `Semantic.Tree.Constructor` and `Core.Tree.Constructor`): the type it
      is declared in at the type's parameters, as before, or at arguments of
      its own, with type variables of its own in scope. Once checked, a type
      declared with `where` is a type like any other, so nothing after the
      checker had to change. Where a constructor is used its own variables
      are unknowns, and the type it makes is what its signature says
- [x] Matching on such a constructor. The type of what is matched is set
      against the type the constructor makes (`refine`, in
      `Semantic.Unify.Type`). Where the first has an unknown, the unknown
      is made what the constructor says. Where it has a type variable of a
      signature, nothing can be made the same, but the variable is known to
      be that for as far as the match reaches: the context of checking
      holds what is known (`equalities`), and making two types the same, and
      finding an instance, look there when they meet a type variable. A
      lambda is now told what type it is to be before its parameter is
      looked at, since a match tells nothing of a type that is not known
      yet (tests `gadt-syntax`, `gadt-expression`, `gadt-indexed`)
- [x] The rest of GADTs, as GHC's extension has them. None of this was in
      the way of the compiler's own source, whose 156 constructors of this
      kind require nothing of their types and are not records.
  - [x] A match anywhere, not only at the parameters of a function: on a
        variable from further out in a `case`, and after another parameter.
        An unknown that has been worked out is taken as what it is where it
        is met, so that what a match told is not lost by stepping out to
        the scope the unknown came from (test `gadt-case`)
  - [x] The types a constructor hides. A variable of the constructor that
        the type it makes does not settle is an unknown where a value is
        made, and where a value is taken apart it is a type that stands for
        itself alone (`Skolem`, in `Semantic.Unify.Type`): the same as
        itself and nothing else, never worked out, though a further match
        may tell what it is for a branch. It may not be part of the type of
        what is matched or of what the match makes, nor of an unknown from
        further out, and a binding may not match a constructor that hides a
        type or tells something of one. A variable given bare to the type
        made, as in `C :: a -> T a`, is what the matched type has there, so
        a type that is only written with `where` is matched as it always
        was (test `gadt-hidden`)
  - [x] What else the declaration may say: names for what a constructor
        holds, the kind of the type in place of some or all of its
        parameters, with or without constructors, and a `deriving` clause.
        Instances are derived by looking at each constructor as a match
        does (test `gadt-record`)
  - [x] A constructor that requires something of its types. For a class, a
        value holds the evidence after everything else it holds
        (`Dictionary`, an expression, and `Held`, evidence that a match
        names). It is asked for where the constructor is used and is there
        to use where the constructor is matched on, with what the class
        requires in turn: the context of checking holds what is given
        beside what is known of types. That two types are the same is
        required without evidence, and means what saying so in the type
        made means (test `gadt-context`)
  - [ ] What is not done. An instance is not derived for a type with a
        constructor that requires a class. A branch that cannot be reached
        is taken without a word, where GHC warns. What a constructor
        requires is known in the branch its pattern leads to, but not in the
        patterns beside it inside the same pattern, so a number matched
        there cannot use it. Types required to be the
        same in the type of a function, a class or an instance are not

- [x] The kind of `Core.Tree.Expression`. The check stopped there with

- [x] `deriving` clauses on types with parameters that are not types of

      instance from a clause is now marked, and when it is checked the class

- [x] Polymorphic components: a constructor that holds something whose

## Track B: further experiments

### Strictness in type schemes

Freddy named strict, multi-argument functions as something performant Haskell
needs that is not in Aith's list, and "Strict functions" is on Hazy's
"Missing" list. This is his design for it, in his words "how I plan to
generalize Haskell 2010 strictness into proper strictness". It is the natural
first experiment once the native backend exists, because the backend is where
it pays off.

The idea is to put strictness on type *schemes*, not on types. A binding's
scheme says how it is evaluated, and there are three calling strategies:

```haskell
-- by need
x :: Int
x = 1

-- by value, may require limits on allowed terms
x :: !Int
x = 1

-- by name
x :: () => Int
x = 1
```

The specification makes this precise with two layers.

- **Terms** have data types `τ ::= [σ] | Int` and evaluate to values.
- **Strategies** have strategy types `σ ::= !τ | ~τ | σ → τ`: strict, lazy,
  and function. Variables are bound to strategies, which is the calculus's
  form of "strictness lives in the scheme".
- A lambda is a strategy, not a term. *Freezing*, `[s]`, is the only way to
  turn a strategy into data that can be passed around, so `[σ → τ]` is a
  closure and `[~τ]` is a suspended value.
- A frozen strict value is opened with `e!`, a frozen lazy one is forced with
  `e~`, and a call `e(s)` passes a strategy as its argument.
- In the semantics `!e` evaluates `e` to a value at once and `~e` captures it
  unevaluated.

By need and by name are kept distinct, as in Freddy's examples (decided by
Chris, 2026-10-09). The specification's rules cannot tell them apart: its
force rule re-evaluates the delayed term every time, because the semantics has
no heap in which to keep the result. The two give the same values and differ
only in cost, so the difference is fixed here in the implementation:

| Scheme | Strategy | When it is evaluated | Result kept |
| - | - | - | - |
| `x :: Int` | by need | at first use | yes, the thunk is overwritten |
| `x :: !Int` | by value | when bound | yes, it is already a value |
| `x :: () => Int` | by name | at every use | no |

The specification's lazy strategy `~τ` is read as by need.

What it gives the compiler: a function whose parameter has scheme `!τ` is
handed an already evaluated value. The caller evaluates before the call, no
thunk is allocated, and the callee never checks whether its argument has been
forced.

How it meets the native pipeline *(proposed)*:

- A `!τ` binder is a plain value in Sequent, a `~τ` binder is a thunk object
  that is updated when forced, and a by-name binder is an object that is run
  again at each use and never updated.
- Freezing is the one place an object is allocated, which is AxCut's `new`.
- A strict binder holds no thunk, so nothing hidden keeps a second reference
  to its value. Strict schemes are therefore also what makes reuse (FBIP)
  dependable; see the open question on reuse under laziness.

Steps:

- [ ] Parse and check strategy annotations on schemes (`!τ`, and `() => τ`
      for by name)
- [ ] Decide the "limits on allowed terms" for by-value bindings; a strict
      top-level binding, for instance, has to be evaluated at some defined
      time
- [ ] Carry strategies through Core into Sequent
- [ ] Tests that tell by need from by name by counting evaluations, since
      their output is otherwise the same
- [ ] Multi-argument functions: a function of known arity called with all its
      arguments at once

Points to raise with Freddy when the work starts:

- Functions take one argument, `σ → τ`. Is a multi-argument function a
  strategy with several parameters, so that no closure is frozen between
  arguments?
- How do strategies on schemes relate to the existing `Levity` kind and
  levity-polymorphic fields (`~!s`)? Can a scheme be polymorphic in its
  strategy?
- A function's result is a term type `τ`, so results are always evaluated. Is
  a lazy result written by returning `[~τ]`?

## Open questions

- **Reuse under laziness.** Reuse depends on a value's count being one at the
  moment it is taken apart. A thunk that captures a value holds a reference to
  it, so laziness will defeat reuse in places where a strict language would
  get it. Freddy's strict schemes are the handle on this: a by-value binder
  holds no thunk. M5's measurements should show how much FBIP plain Haskell
  2010 code gets, and the strictness experiment how much annotations add.
- **Regions and uniqueness in the type system.** A thunk can outlive the scope
  that made it. Aith was strict and did not face this, and Freddy has no
  answer yet.
- **How experiments are switched on.** Hazy's backwards-compatible extensions
  cannot currently be toggled; Freddy may look into it.
- **The standard library.** See the note under M6.
- **Maintainability.** Freddy is unsure how maintainable AI-assisted work is
  over the long term and wants quality kept high. Changes here should stay
  small and readable enough that he could review any one of them.
